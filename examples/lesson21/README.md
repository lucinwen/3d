# 第 21 讲实验：不可变快照、依赖检查与发布回滚

这是一个使用 **Python 标准库**的可运行教学实验。输入是脚本内声明的两件微型合成网格，共 4 个三角面；不是生产数据、真实质量评测或学习者已经完成的练习。

## 文件

- `versioning_lineage_lab.py`：完整代码，Python 3.10+，无第三方依赖。
- `example-report.json`：直接执行该脚本生成的完整 JSON 输出，没有人工摘录或改写报告字段。

## 运行

在仓库根目录执行：

```bash
python examples/lesson21/versioning_lineage_lab.py --output examples/lesson21/example-report.json
```

本次实际环境为 **Python 3.12.14**，命令退出码为 **0**。脚本正常运行会输出完整 JSON；任一预期应拦截的候选意外通过时，会抛出 `AssertionError`，不伪造成功报告。

每次执行使用自己的临时对象目录，结束后删除临时目录，只保留指定的报告文件。这样不会覆盖已有项目数据。报告中的两份发布清单、哈希和运行记录是实验结果；它不提供可长期访问的外部对象存储服务。

## 输入与身份

两个网格使用右手坐标系、Z 向上、单位米，坐标为整数。每个网格有 4 个顶点和 2 个三角面。合成标签 `0=base`、`1=upper` 仅供绑定检查，没有真实部件语义验证含义。

每个样本记录逻辑资产身份 `asset_id`、人为指定的家族 `family_id`、来源字节哈希 `source_hash`、精确网格哈希 `mesh_hash`、标签哈希 `annotation_hash` 和 train/test 划分。家族来自已知合成输入，不是算法发现的近重复簇。

同一网格的带缩进 JSON 与紧凑 JSON 字节不同，因此 SHA-256 不同，解析后的顶点与面仍相同。这说明字节身份和逻辑资产身份不能混用。本实验采用严格限定的本地序列化约定：字符串键的字典、列表、字符串、整数、布尔和 null；不接受浮点数；UTF-8、字典键排序、固定紧凑分隔符。**这不是完整 RFC 8785 实现，也不是跨格式几何同一性算法。**

## 运行步骤与机制

1. 将代码、两份源网格、规范序列化网格、标签、本体和质量策略放入按 SHA-256 寻址的对象目录；常规写入不覆盖已存在对象。
2. 将操作、代码哈希、输入对象集合、完整样本配置、划分版本、Python 版本和策略哈希保存为 recipe 对象。
3. 构建发布清单，检查必需字段、唯一资产 ID、划分、家族隔离、标签与网格/本体绑定。
4. 遍历完整依赖闭包，逐个读取对象并重算 SHA-256；缺失对象、损坏对象和 recipe 输入遗漏均阻止发布。
5. 验证完成后，将新的 `current.json` 临时文件写完，再用同一文件系统中的 `os.replace` 切换指针。
6. 将示例策略阈值从 80 改为 85，产生第二个 recipe 和第二份发布快照。样本成员保持不变；这里只演示策略身份变化，**没有实施质量评分或声称样本达到某个阈值**。
7. 重跑相同发布配置：内容 ID 相同，运行 UUID 不同。
8. 注入七种故障并确认旧指针未改变；再将指针回滚到第一份快照，核验第二份快照仍可读取。

这里的图是**内容对象依赖图**，边方向为“被依赖对象 → 引用该对象的对象”。它不是完整的 Entity/Activity/Agent 生产血缘模型。运行记录独立保留；不会把一个无变化运行错误地建成 `hash → 同一个 hash` 自环。真实生产系统还需为实体修订、活动和责任主体分别建模。

## 实际执行结果

| 检查项 | 本次结果 |
|---|---|
| 合成资产 / 三角面 | 2 / 4 |
| 不同发布快照 | 2 |
| 每份发布清单的依赖闭包对象数（含自身） | 11 |
| 两个有效快照合并后的去重依赖边数 | 40 |
| 网格 A 的下游对象数 | 5：1 个标注、2 个 recipe、2 份发布清单 |
| 网格 A 影响的发布快照 | 2 |
| 相同配置重复执行 | 发布哈希相同，run UUID 不同 |
| 回滚 | 指针恢复第一份快照，两份快照均保留 |

故障注入逐项得到：

| 注入故障 | 预期且实际发生的阻断原因 |
|---|---|
| 样本缺少 `family_id` | `missing_sample_fields` |
| 同一家族分布在 train/test | `family_split_leakage` |
| 网格面顺序改变、面数不变，仍复用旧标注 | `annotation_mesh_binding_mismatch` |
| 来源对象哈希指向不存在对象 | `missing_object` |
| recipe 输入集合为空，遗漏实际输入 | `recipe_input_or_config_mismatch` |
| 发布本体改变，标注仍绑定旧本体 | `annotation_ontology_mismatch` |
| 对象文件被外部直接修改 | `hash_mismatch` |

七种故障均在切换发布指针前被拦截，报告为每种故障记录 `published_pointer_unchanged: true`。损坏字节的演示故意绕过 Store API，在临时测试目录直接改写文件；随后恢复原始字节，仅用于证明读取校验能发现破坏。

报告中 `runs` 的 UUID 每次执行会变化，因此不能要求两份完整报告逐字相等。相同脚本和 Python 版本下，应比较发布哈希、recipe 哈希、依赖关系和检查结果。修改脚本或环境版本会改变 recipe，以及依赖它的发布哈希，这是该身份设计的预期行为。

## 阅读代码的入口

先读 `canonical_bytes()` 与 `Store.get()`，理解可复核的字节身份；再读 `validate_release()`，理解标签绑定、家族隔离和输入覆盖；随后读 `publish()`，看清验证与指针切换的先后关系；最后读 `downstream()` 与 `run_lab()` 的故障注入。

依赖图的遍历按节点与边处理，时间复杂度为 O(V+E)；完整校验还要读取全部对象字节，所以总耗时同时取决于读取字节总量。`downstream()` 返回可能受影响的对象，不证明这些对象已经受到实际损害。

## 适用范围和未实现项

- 本地、单写者实现；没有多进程锁、比较并交换（CAS）、分布式事务或并发发布冲突处理。`os.replace` 的整文件切换不等于多写者事务。
- 对指针文件执行了 `fsync`，但没有实现完整对象/目录的断电持久性协议。常规写入失败不会成为已发布快照；对象暂存后的清理与崩溃恢复还需独立实现。
- 没有 DCC 文件解析、几何合法性穷尽检查、语义标注正确性判断、授权审核、真实质量评分、近重复发现、模型训练或校准。
- 没有对象删除/撤销策略、备份恢复、多级存储、保留期、数字签名或访问控制；内容哈希不等于来源可信证明。
- 家族、标签本体与划分是显式输入。输入元数据本身错误时，哈希不会替你发现其语义错误。
- 小数据整段读取方便教学。大规模实现需要流式哈希、分片清单、索引和受控缓存。

## 练习

1. 将一个样本的 `annotation_hash` 换成另一个样本的标签，解释预期的阻断原因。
2. 为同一家族增加另一版本网格，先放到相同 split，再放到不同 split，观察差别。
3. 给发布清单增加 `task_profile_hash`，同步修改依赖 schema、recipe 和验证逻辑，说明遗漏任一处的风险。
4. 设计并发发布时的 expected-head 检查，不要把当前单写者演示直接称为生产并发方案。

这些是待学习者完成的练习，脚本已由维护者运行不代表学习者已经掌握。
